# DexBotX backend

NestJS API + sharded Discord bot (discord.js v14) + BullMQ worker. Postgres on Supabase (Drizzle ORM), Redis for sessions, cache, rate limits, pub/sub and the job queue.

```
Browser ──► Next.js (same origin) ──/api/*──► NestJS API ──► Supabase Postgres
                                               │  ▲
                                               ▼  │ pub/sub (cache invalidation)
                                             Redis ◄──── Bot shards (discord.js) ◄── Discord gateway
                                               │            (validate, then enqueue a compact job)
                                               ▼
                                          BullMQ queue ──► Worker(s): render card, post via Discord REST
```
Shards only validate an event and enqueue a job. Workers render the image and post it, retry with backoff, and skip permanent failures (for example missing channel permissions). Scale workers independently of shards.

The browser only talks to the dashboard origin. Next.js rewrites `/api/*` to this API, so the session cookie is first-party and there is no CORS surface.

## Quick start

```bash
cd backend
cp .env.example .env          # fill it in (see below)
npm install
npm run db:generate           # only after changing src/db/schema.ts
npm run build && npm run db:migrate
npm run db:backfill-guild-data # optional once after deploying guild-data migration
npm run start:dev             # API on :4000
npm run start:bot:dev         # bot, in a second terminal
npm run start:worker:dev      # queue worker, in a third terminal
```

Or with Docker (API + bot + worker + Redis + one-shot migration): set `REDIS_PASSWORD` in `backend/.env`, then run `docker compose --env-file backend/.env up -d --build` from the repo root.

### Discord Developer Portal
1. Create an application; copy **Client ID**, **Client Secret** and the **Bot token** into `.env`.
2. OAuth2 → Redirects → add `<WEB_URL>/api/auth/callback` (e.g. `http://localhost:3000/api/auth/callback`).
3. Bot → enable **Server Members Intent** (needed for join/leave events; Discord requires verification at 100 servers).
4. The invite link is generated by the API with permissions `1099780443270` (existing channel/message permissions plus moderation and View Audit Log). Administrator is intentionally not requested. Existing servers must re-authorize with the updated invite link. When posting is denied in a channel, the bot uses Manage Roles to create or reuse a `DexBotX` role and add a per-channel permission overwrite. See [DEPLOYMENT.md](./DEPLOYMENT.md) for command deployment.

### Supabase
- `DATABASE_URL`: the **session pooler** string (port 5432) or the direct connection. Do not use the transaction pooler (6543) for these long-running servers.
- Run `npm run db:migrate` once per deploy.
- Migration `0001_guild_data` renames the guild key/flags to `guild_id` and `bot_present`, adds guild-scoped channel, role, and template tables plus `last_synced_at`, preserves existing rows, and removes the cascading-delete behavior. Existing Redis/API-only channel data has no durable SQL source, so run `npm run db:backfill-guild-data` after migration (or let bot startup/periodic sync populate active guilds).
- Migration `0002_admin_operations` adds `guilds.last_message_at` and the `admin_audit` table. Apply all migrations before starting updated API, bot, or worker processes; all processes must connect to the same database.
- Row Level Security is already enabled on every table by the migration (no policies), so Supabase's public REST API cannot read or write your data. Only this backend, connecting as the database owner, can. An e2e test fails if a table is added without RLS.
- Custom card backgrounds (optional): set `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` (service role, server-side only). The backend creates a **private** bucket on first upload; without these variables uploads are disabled.
- Use a paid project in production: free projects pause when idle, which would take the bot offline.

## Environment
See `.env.example`. Required: `WEB_URL`, `DATABASE_URL`, `REDIS_URL`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN`, `SESSION_ENCRYPTION_KEY` (`openssl rand -hex 32`). Invalid config stops the process at boot with a readable list of problems.

`ADMIN_USER_IDS` is a comma-separated list of Discord user IDs (17–20 digits) allowed into the admin console, for example `123456789012345678,234567890123456789`. It defaults to empty, which disables admin access for everyone. Configure it only on backend processes; frontend state is never used to authorize admin requests.

`WS_PUBLIC_URL` is the public native WebSocket endpoint returned by `POST /ws/ticket` (for example `wss://api.example.com/ws`). The endpoint requires an authenticated dashboard session; tickets are single-use and expire after 30 seconds. In production, configure a public `wss://` URL and ensure the API host/proxy accepts WebSocket upgrades.

## Production on Render

For the production dashboard at `https://dexbotx.vercel.app` and API at `https://dexbotx-zq8g.onrender.com`:

- Configure the Render API service with the Node runtime and root directory `backend`; use `npm ci --include=dev && npm run build && npm prune --omit=dev` as its build command and `npm run start` as its start command. The backend pins Node to the 22.x line because an open-ended engine range lets Render select a newer major. Set `NODE_ENV=production` and `WEB_URL=https://dexbotx.vercel.app`. A production HTTP or localhost `WEB_URL` is rejected at startup. Set Render's health check path to `/health/ready`.
- Set production `DATABASE_URL`, managed `REDIS_URL`, Discord credentials, and `SESSION_ENCRYPTION_KEY` in Render's environment. Keep `COOKIE_DOMAIN` unset so the secure host-only cookie is returned through Vercel's same-origin API proxy.
- Create separate Render background workers using the Node runtime and root directory `backend`. Use `npm ci --include=dev && npm run build && npm prune --omit=dev` as each build command, then `npm run start:bot` for the bot and `npm run start:worker` for the queue worker. Configure both with the same database, Redis, and Discord environment as the API.
- Register `https://dexbotx.vercel.app/api/auth/callback` in Discord Developer Portal → OAuth2 → Redirects. This exact URL is derived from `WEB_URL`.

After deployment, `/auth/login` should redirect to Discord with that callback URL. Check `/health/ready` on the Render API and `/api/health/ready` through Vercel.

## API (all JSON, session cookie required unless noted)
| Method | Path | Notes |
|---|---|---|
| GET | `/auth/login` | public, starts Discord OAuth2 (state bound to the browser) |
| GET | `/auth/callback` | public, completes login, sets the session cookie |
| GET | `/auth/me` · POST `/auth/logout` | logout destroys the session and revokes the Discord token |
| GET | `/guilds` | servers the user can manage; includes an invite URL where the bot is missing |
| GET | `/guilds/:guildId` | server details plus welcome and goodbye config |
| GET | `/guilds/:guildId/channels` | text and announcement channels, grouped by category |
| GET | `/guilds/:guildId/roles` | guild-scoped roles for dashboard selectors |
| POST | `/guilds/:guildId/refresh` | full Discord sync; Manage Server required; 30-second per-guild cooldown |
| GET | `/events/guilds` | authenticated server-sent events when the bot joins or leaves a server |
| PUT | `/guilds/:guildId/messages/:kind` | save config, `kind` = `welcome` or `goodbye` |
| DELETE | `/guilds/:guildId/messages/:kind` | reset only that message kind to defaults; settings and audit record commit atomically |
| POST | `/guilds/:guildId/messages/:kind/preview` | renders a real PNG using the user's avatar |
| POST | `/guilds/:guildId/assets/background` | multipart field `file`; validated and re-encoded to JPEG (2 MB cap, decompression-bomb safe), stored privately; returns a `path` for `image.backgroundPath` |
| POST | `/guilds/:guildId/messages/:kind/test` | posts a test message; explains missing channel permissions instead of failing silently |
| GET | `/templates/presets` | public, immutable 24-hour cache of preset templates |
| GET | `/flags` | public, cached flag endpoint exposing only `maintenance` |
| GET | `/health` · `/health/ready` | liveness and readiness (database + Redis) |
| GET | `/metrics` | Prometheus; needs `Authorization: Bearer $METRICS_TOKEN`, disabled when unset |

### Admin API

All `/admin/*` routes require a valid session and a user ID listed in `ADMIN_USER_IDS`. Unauthorized requests deliberately return 404. State-changing admin requests require the dashboard origin and are recorded in `admin_audit`. The Admin link in the frontend is only a convenience; it is not an authorization boundary.

| Method | Path | Notes |
|---|---|---|
| GET | `/admin/me` | verifies admin access |
| GET | `/admin/overview` | service health, totals, shard activity, charts, and queue state |
| GET | `/admin/rate-limits` | Discord API call counts, recent 429s, cache hit rates, and cooldown |
| GET | `/admin/guilds?search=&page=` | searchable installed guild list |
| GET | `/admin/guilds/:id` | guild settings, channel posting status, and recent failures |
| POST | `/admin/guilds/:id/resync` · `/disable` | invalidate cached guild data or disable welcome and goodbye |
| POST | `/admin/guilds/:id/leave` | requires `{ "confirm": "<exact guild name>" }` |
| GET | `/admin/failures` | sanitized failed-job details |
| POST | `/admin/failures/:jobId/retry` · `/admin/failures/clear` | retry a failed job or clear all after confirmation |
| GET | `/admin/users` | recent login IDs/usernames/avatars and active session count; excludes emails and tokens |
| POST | `/admin/users/:id/revoke` | revoke all Redis sessions for a user |
| GET | `/admin/content` | preset usage and stored background metadata |
| POST | `/admin/content/background` | delete with `{ "path": "...", "confirm": true }`; clears references in guild settings |
| GET | `/admin/flags` · PUT `/admin/flags` | read or validate/update the Redis-backed feature flags |
| GET | `/admin/audit?page=&action=` | newest-first, 50 records per page; optional exact action filter |

Feature flags are `maintenance` (boolean), `musicEnabled` (boolean), `socialEnabled` (boolean), and `messageRatePerMinute` (integer from 0 to 1000). Maintenance skips all welcome and goodbye posts; a zero message rate pauses them. The API and bot read the same Redis hash so changes are shared across processes. Public `GET /flags` returns only the maintenance state and caches it for 30 seconds.

## Performance
- The API enables gzip/Brotli response compression and emits a `Server-Timing: app;dur=...` header on responses.
- JSON `GET` responses include an ETag and default to `Cache-Control: private, no-cache`; clients can revalidate with `If-None-Match`. Explicit public caching (presets) and `no-store` routes keep their configured behavior.
- Discord's current-user guild list is fetched with cursor pagination (200 items per request, up to 1,000) and cached in Redis. Guild channels, roles, metadata, and settings use the existing guild-scoped cache-aside reads and indexed Postgres lookups.
- The backend uses a pooled `postgres`/Drizzle connection. Set `DATABASE_POOL_MAX` to tune each process; use the Supabase Session Pooler (port 5432) or direct connection for long-running API, bot, and worker processes.

## Security model
- **Auth:** Discord OAuth2 (`identify guilds`), single-use `state` bound to the browser. The session lives in Redis behind an httpOnly, SameSite=Lax cookie; Discord tokens are stored AES-256-GCM encrypted, never in plain text.
- **Authorization:** every `/guilds/:guildId/*` route re-checks server side that the user has Manage Server (or owns the server) and that the bot is installed. Guild ids from the client are never trusted.
- **CSRF:** state-changing requests must carry the dashboard `Origin`/`Referer`; anything else is rejected.
- **Rate limits:** Redis sliding counters per user (per IP when anonymous), stricter on login, preview and test sends.
- **Live server list:** bot join/leave events are published through Redis Pub/Sub and delivered over the authenticated `/events/guilds` stream; the dashboard refreshes the active guild list only when membership changes, without periodic polling.
- **Live dashboard updates:** `POST /ws/ticket` issues a short-lived, single-use ticket for the native `/ws` endpoint. The API checks the dashboard Origin and active session, limits each user to five connections, authorizes guild-room joins, and forwards sanitized guild events from Redis Pub/Sub.
- **Settings writes:** the settings upsert and audit-log entry are one Postgres transaction; `DELETE /guilds/:guildId/messages/:kind` resets only that message type to defaults. Redis caches are invalidated after the transaction commits.
- **Client metadata cache:** the frontend persists only validated server/channel display metadata in user-scoped local storage for up to seven days. It still fetches the API on entry/refresh, and bot membership/channel events invalidate the active query. Message settings are never persisted in browser storage.
- **Output safety:** user-controlled names are markdown-escaped, `@everyone`/`@here` are defused, and bot messages use restricted `allowed_mentions`. The bot never posts to a channel that is not in the member's own server.
- **Transport:** Helmet headers, request body limit of 32 KB, strict zod validation (unknown keys rejected), Sentry for errors, pino logs.

## Scaling
- Sharding: `SHARD_COUNT=1` by default. Set a larger integer when required; each shard is a process managed by the bot manager.
- Redis connections: each API instance and bot shard uses one shared command client and one shared subscriber client; settings invalidation, guild events and realtime updates share that subscriber. Queue producers reuse the command client. Each worker also uses BullMQ's worker and blocking connections. Connections are named (`api:main`, `api:sub`, `shard0:main`, etc.) and closed during shutdown; expected Redis client counts are two for API/shards and four for a worker.
- The API is stateless: run N replicas behind a load balancer. Sessions, rate limits and the config cache are in Redis; config changes reach the bot's in-process cache through Redis pub/sub.
- Welcome cards are rendered by workers: `WORKER_CONCURRENCY` jobs per process, a global 40 jobs/s limiter, 5 attempts with exponential backoff, and `docker compose up -d --scale worker=3` to add capacity. A join raid queues up instead of exhausting shard CPU.
- Metrics: `dexbotx_http_request_duration_seconds`, `dexbotx_discord_rest_calls`, `dexbotx_member_events_total`, `dexbotx_queue_jobs`, and `redis_connections` (plus default process metrics). Discord REST calls are counted in shared Redis by method and normalized route. Redis client count is read from `INFO clients`. Set `WORKER_METRICS_PORT` to scrape workers too.
