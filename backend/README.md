# DexBotX backend

NestJS API + sharded Discord bot (discord.js v14) + BullMQ worker. Postgres on Supabase (Drizzle ORM), Redis for sessions, cache, rate limits, pub/sub and the job queue.

```
Browser ──► Next.js (same origin) ──/api/*──► NestJS API ──► Supabase Postgres
                                               │  ▲
                                               ▼  │ pub/sub (cache invalidation)
                                             Redis ◄──── Bot shards (discord.js) ◄── Discord gateway
                                               │            (validate, then enqueue a compact job)
                                               ▼
                                          BullMQ queue ──► Worker(s): render card, post via Discord REST
```
Shards only validate an event and enqueue a job. Workers render the image and post it, retry with backoff, and skip permanent failures (for example missing channel permissions). Scale workers independently of shards.

The browser only talks to the dashboard origin. Next.js rewrites `/api/*` to this API, so the session cookie is first-party and there is no CORS surface.

## Quick start

```bash
cd backend
cp .env.example .env          # fill it in (see below)
npm install
npm run db:generate           # only after changing src/db/schema.ts
npm run build && npm run db:migrate
npm run start:dev             # API on :4000
npm run start:bot:dev         # bot, in a second terminal
npm run start:worker:dev      # queue worker, in a third terminal
```

Or with Docker (API + bot + worker + Redis + one-shot migration): `docker compose up -d --build` from the repo root.

### Discord Developer Portal
1. Create an application; copy **Client ID**, **Client Secret** and the **Bot token** into `.env`.
2. OAuth2 → Redirects → add `<WEB_URL>/api/auth/callback` (e.g. `http://localhost:3000/api/auth/callback`).
3. Bot → enable **Server Members Intent** (needed for join/leave events; Discord requires verification at 100 servers).
4. The invite link is generated by the API with permissions `52224` (View Channel, Send Messages, Embed Links, Attach Files). Administrator is intentionally not requested.

### Supabase
- `DATABASE_URL`: the **session pooler** string (port 5432) or the direct connection. Do not use the transaction pooler (6543) for these long-running servers.
- Run `npm run db:migrate` once per deploy.
- Row Level Security is already enabled on every table by the migration (no policies), so Supabase's public REST API cannot read or write your data. Only this backend, connecting as the database owner, can. An e2e test fails if a table is added without RLS.
- Custom card backgrounds (optional): set `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` (service role, server-side only). The backend creates a **private** bucket on first upload; without these variables uploads are disabled.
- Use a paid project in production: free projects pause when idle, which would take the bot offline.

## Environment
See `.env.example`. Required: `WEB_URL`, `DATABASE_URL`, `REDIS_URL`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN`, `SESSION_ENCRYPTION_KEY` (`openssl rand -hex 32`). Invalid config stops the process at boot with a readable list of problems.

## API (all JSON, session cookie required unless noted)
| Method | Path | Notes |
|---|---|---|
| GET | `/auth/login` | public, starts Discord OAuth2 (state bound to the browser) |
| GET | `/auth/callback` | public, completes login, sets the session cookie |
| GET | `/auth/me` · POST `/auth/logout` | logout destroys the session and revokes the Discord token |
| GET | `/guilds` | servers the user can manage; includes an invite URL where the bot is missing |
| GET | `/guilds/:guildId` | server details plus welcome and goodbye config |
| GET | `/guilds/:guildId/channels` | text and announcement channels, grouped by category |
| PUT | `/guilds/:guildId/messages/:kind` | save config, `kind` = `welcome` or `goodbye` |
| POST | `/guilds/:guildId/messages/:kind/preview` | renders a real PNG using the user's avatar |
| POST | `/guilds/:guildId/assets/background` | multipart field `file`; validated and re-encoded to JPEG (2 MB cap, decompression-bomb safe), stored privately; returns a `path` for `image.backgroundPath` |
| POST | `/guilds/:guildId/messages/:kind/test` | posts a test message; explains missing channel permissions instead of failing silently |
| GET | `/templates/presets` | public, cacheable preset templates |
| GET | `/health` · `/health/ready` | liveness and readiness (database + Redis) |
| GET | `/metrics` | Prometheus; needs `Authorization: Bearer $METRICS_TOKEN`, disabled when unset |

## Security model
- **Auth:** Discord OAuth2 (`identify guilds`), single-use `state` bound to the browser. The session lives in Redis behind an httpOnly, SameSite=Lax cookie; Discord tokens are stored AES-256-GCM encrypted, never in plain text.
- **Authorization:** every `/guilds/:guildId/*` route re-checks server side that the user has Manage Server (or owns the server) and that the bot is installed. Guild ids from the client are never trusted.
- **CSRF:** state-changing requests must carry the dashboard `Origin`/`Referer`; anything else is rejected.
- **Rate limits:** Redis sliding counters per user (per IP when anonymous), stricter on login, preview and test sends.
- **Output safety:** user-controlled names are markdown-escaped, `@everyone`/`@here` are defused, and bot messages use restricted `allowed_mentions`. The bot never posts to a channel that is not in the member's own server.
- **Transport:** Helmet headers, request body limit of 32 KB, strict zod validation (unknown keys rejected), Sentry for errors, pino logs.

## Scaling
- Sharding: `SHARD_COUNT=auto` (Discord recommends the count; required from 2,500 servers). Each shard is a process; run the manager on one host or split by shard ids later.
- The API is stateless: run N replicas behind a load balancer. Sessions, rate limits and the config cache are in Redis; config changes reach the bot's in-process cache through Redis pub/sub.
- Welcome cards are rendered by workers: `WORKER_CONCURRENCY` jobs per process, a global 40 jobs/s limiter, 5 attempts with exponential backoff, and `docker compose up -d --scale worker=3` to add capacity. A join raid queues up instead of exhausting shard CPU.
- Metrics: `dexbotx_http_request_duration_seconds`, `dexbotx_member_events_total` and `dexbotx_queue_jobs` (plus default process metrics). Set `WORKER_METRICS_PORT` to scrape workers too.
